**Answer 1 — “How would you identify the key onboarding barrier?”**

Suggested speaking time: 60 seconds. This is a hypothetical approach.

> “I would first define the value a new user should reach and the activation event that represents it. Then I would map the steps leading to that event and check where eligible users stop progressing, using consistent event definitions and time windows. I would segment the funnel where relevant and combine the quantitative pattern with support issues or user feedback to understand the reason for the drop-off.
>
> “I would distinguish between a usability problem, a technical blocker, and a mismatch between what users expect and what the product offers. Those require different responses. I would prioritize a problem using its impact, the strength of the evidence, and the cost of addressing it, then test the smallest appropriate change. My past checklist and support-review coordination is relevant context, but I would not claim that this full diagnostic process is something I already performed in that project.”

Follow-ups: if asked which step failed in the actual project, do not invent one; explain that it has not been supplied. If asked why a checklist is the right fix, say it depends on the diagnosed problem. If asked how to transfer the method, start with the target product’s own value event rather than importing a generic completion metric.

**Answer 2 — “How would you work with support and engineering to deliver a change?”**

Suggested speaking time: 60–90 seconds.

> “My relevant experience is coordinating an onboarding checklist and weekly issue reviews with support. Engineering delivered the platform changes, and I have not managed people, so I would distinguish coordination from technical ownership or line management.
>
> “For a new initiative, I would align the teams on the user problem, intended outcome, constraints, and accountable owners. I would separate issues that support can address through guidance from changes requiring engineering work. I would agree on the problem and acceptance criteria with engineering, then compare options using user impact, evidence, dependencies, and effort.
>
> “If capacity were limited, I would consider a narrower product fix or a temporary support workaround and make the trade-offs visible. Regular reviews would be for resolving blockers and confirming decisions, not just reporting activity. If a priority conflict remained, I would take the concrete options to the accountable decision-maker while keeping implementation responsibility with engineering.”

Follow-ups: describe any actual disagreement only if you can recall it truthfully; do not infer authority over the engineering roadmap; evaluate coordination through completed decisions and delivery, not number of meetings.

**Answer 3 — “How would you evaluate activation and retention impact?”**

Suggested speaking time: 90 seconds. This is a hypothetical evaluation plan.

> “I would define activation as a meaningful event completed by an eligible user within a specified window, and define retention separately using a fixed cohort and an appropriate return activity. I would validate the event tracking and denominators before interpreting changes.
>
> “Where feasible, I would assign eligible users or accounts to an intervention and a comparison group before exposure, avoiding contamination and giving both groups comparable follow-up time. I would keep other changes consistent where possible, because a checklist introduced alongside platform changes cannot automatically be credited with the combined result. I would assess activation, retention, and relevant guardrails such as support burden or errors.
>
> “If activation improved but retention did not, I would investigate whether the activation event captured superficial completion rather than lasting value. I would examine segment differences and uncertainty before expanding the change. If a sound experiment were unavailable, I would use the strongest credible comparison and explain its limitations. I would not claim causality solely because conversion increased after rollout.”

Follow-ups: explain the denominator as the pre-defined eligible cohort; distinguish percentage points from relative change; avoid claiming you ran an experiment, since that is not established here. For example, 10% to 12% is a hypothetical 2-percentage-point or 20% relative rise, not evidence about the actual project.
