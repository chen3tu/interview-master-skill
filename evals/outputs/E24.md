These are three synthetic tasks for the same shared shopping-list product. The solutions are framework-neutral designs; no code, platform-specific APIs or tests have been executed.

## Frontend: stale search results

**Task and input:** A user types “milk” and then “oat milk.” The second search returns first; the late “milk” response must not replace it. The search must also work with keyboard input and slow networks.

**Worked solution:** Keep query text, a monotonically increasing request generation, loading state, results and error state explicit. Increment the generation whenever the query changes, including when it becomes empty; a request captures that generation, and both its success and error handlers may update state only if it still matches the current generation. Clearing the query immediately invalidates pending work and clears the displayed results. Retry creates a new generation so a previous attempt cannot overwrite the retry.

For example, milk starts at generation 7 and oat milk at 8: response 8 displays oat-milk results; response 7 is discarded. An old error is discarded under the same rule. Cancellation may reduce wasted work, but the generation guard remains because cancellation can race with completion. Preserve focus and expose distinct loading, empty and error states through labeled controls and appropriate status announcements; results from a different query must not appear as current.

**Alternative:** Cache by normalized query with an explicit freshness policy and show cached results for the current query while revalidating. It still needs generation checks; debounce alone only reduces requests and does not fix the race.

**Failure test:** Resolve requests in reverse order, reject an old request after a new one succeeds, clear the field while work is pending, and retry after failure. Expected: only the current attempt changes current state, empty input stays empty and keyboard focus remains usable. Also test repeated identical text across different request generations to ensure an older attempt cannot overwrite a newer one merely because their strings match.

## Mobile: offline synchronization

**Task and input:** Two devices edit the same shared list item offline. Device A changes quantity from one to two while device B deletes it; the app may restart before synchronization completes.

**Worked solution:** Persist each local change and its queue record atomically before saying it is saved locally. Each operation has a stable operation ID, item ID, base version and intended change; show pending, synced, failed or conflict status separately. The server deduplicates operation IDs and checks authorization plus the base version before applying a mutation. On reconnect, send with bounded backoff and retain the same ID across retries; recover the durable queue after restart.

If deletion is committed first, the stale quantity edit encounters a tombstone/version conflict. Use an explicit product policy: preserve the deleted item and the pending edit as recoverable conflict data, then let the user choose whether to restore with quantity two or keep the deletion. Do not silently recreate or discard the edit. A restore is a new authorized operation against the current version, and permission revocation prevents applying queued changes while preserving a clear recoverable local status.

**Alternative:** Automatically merge independent field changes and surface only semantic conflicts such as delete-versus-edit. Last-write-wins is simpler but may discard valid intent; client wall clocks alone should not determine which change survives. Batch nonurgent sync and measure resource use rather than maintaining continuous polling.

**Failure test:** Kill the app after the server commits a quantity increment but before the acknowledgment arrives. After restart, retry the same operation ID and verify the quantity changes only once and the pending queue clears after its status is confirmed. Also test concurrent deletion, duplicate delivery, partial batch success and access revoked before reconnect; no acknowledged local edit should vanish without a visible recovery or resolution outcome.

## Backend: migrate list storage

**Task and input:** Move shared lists from store A to B while writes continue, without losing acknowledged writes. Assume per-record versions and no transaction across stores; the source supports an atomic business-update-plus-outbox transaction for this worked solution.

**Worked solution:** Keep A authoritative while each write commits its update and an outbox record in A's transaction. Replay outbox events into B with stable operation identities, version checks and deletion tombstones; checkpoint only after durable application, and make replays safe. Backfill from a consistent snapshot while streaming changes, rejecting stale backfill records so an older quantity or deleted item cannot reappear. Reconcile list membership, quantities, permissions and tombstones, not merely row counts.

Shadow reads and then canary reads from B, with correctness and lag gates. Before transferring write authority, fence old writers through a tested routing/epoch mechanism and ensure requests can be durably accepted or retried during the transition; switch only after catch-up and reconciliation. Establish a supported durable B-to-A synchronization/recovery path before promising rollback after B accepts writes. Before that stage, returning reads to A is straightforward; afterward, blindly switching back would risk losing B-only changes.

**Alternative:** A verified durable change-data-capture mechanism can replace the outbox if source transactions are unavailable. A final short write pause can simplify reconciliation, but is only an option if the continuous-write requirement is relaxed; without a reliable capture or recovery guarantee, postpone cutover.

**Failure test:** Crash a replay worker after applying an event but before checkpointing, deliver an old backfill after a delete, let B become unavailable, and exercise rollback after a B-only write. Expected: retries have no duplicate effect, tombstones survive, A remains safely authoritative before cutover, and any post-cutover rollback preserves acknowledged B writes. Delay cutover if lag grows or unresolved semantic discrepancies remain.
