Both candidates must protect acknowledged writes. The difference is the breadth of responsibility and evidence expected, not permission for a junior design to lose data. Neither has supplied actual work history, so both answers below are hypothetical design demonstrations.

| Area | Campus candidate | Senior candidate |
|---|---|---|
| Core reasoning | Trace a write, explain which store is authoritative and identify partial failure | Define invariants across the migration and ownership transition |
| Replication | Understand durable replay, retries and idempotency | Choose and validate the capture mechanism, ordering and recovery guarantees |
| Backfill | Explain why old snapshot data must not overwrite a new update | Plan capture boundaries, deletes, reconciliation and schema compatibility |
| Testing | Walk through a worker crash, replay and out-of-order update | Exercise capacity, failover, split ownership, rollback and disaster recovery |
| Delivery responsibility | Explain assumptions, uncertainties and when to seek review | Assign operational owners, establish decision gates and manage cross-team risk |
| Evidence standard | Scoped design reasoning can be sufficient for an exercise | A good design is still not proof of production delivery without real history |

Use this synthetic task: move customer preferences from A to B while accepting writes. A is initially authoritative; there is no cross-database transaction. Assume A supports an atomic transaction containing the business update and a durable outbox record, and each entity has a monotonic version. Reads may lag by up to five seconds. These are exercise assumptions, not claims about a particular database product.

**Worked campus answer**

“I would keep A as the write authority while populating B. A request would commit the preference update and a durable change record together in A, then acknowledge success. A worker would apply that record to B using the entity ID and version, so a retry does not repeat an effect and an older event does not overwrite a newer value. I would include deletion records too.

“For the existing data, I would take a snapshot tied to a replay position and backfill it while changes continue to stream. The destination's version check would prevent an old backfill row from replacing a later update. I would compare values and versions, not just row counts, and test a crash after A commits but before B updates, a retry after B updates, and an older event arriving late. Each case should preserve the source write and converge in B.

“I would move a small portion of reads to B after verifying correctness and acceptable lag. I would keep writes on A until the team has reviewed the authority-transfer and recovery procedure; ordinary dual writes are not atomic, and simply changing both write endpoints risks a loss window. If the source cannot support the assumed atomic outbox, I would ask about its supported durable change-capture mechanism before relying on the design.”

This answer demonstrates a coherent scoped solution. The candidate need not pretend to have operated a large migration or personally owned its final approval.

**Worked senior answer**

“I would start by making the invariant and authority explicit: every acknowledged write must be durably recoverable, and only one authority may accept a given entity's writes at a time. I would confirm the actual source's capture, snapshot, ordering and failover guarantees before committing to an implementation. Under the stated assumptions, I would commit the update and outbox record in A, replicate with version-aware idempotent application, retain tombstones and durable consumer checkpoints, and control replay retention so outages cannot silently drop history.

“I would establish a snapshot/replay boundary, backfill while streaming changes, and reconcile logical values, versions and deletions. Shadow reads would reveal divergence before canary reads affect users. Migration gates would include reconciled data, sustained lag within the five-second read target under representative load, sufficient recovery capacity, and a tested runbook with named owners. If replication cannot keep up, I would delay cutover and fix the bottleneck rather than hide the backlog with a larger timeout.

“For write cutover, I would fence old-authority writes with an epoch or routing mechanism whose correctness the system can enforce. Requests arriving during the transition would need a durable acceptance path and consistent retry/idempotency semantics; the final source position must be drained and reconciled before B becomes authoritative. If the system cannot support that transfer while meeting the availability requirement, I would keep A authoritative while the gap is resolved. I would not claim a zero-interruption cutover based on an untested routing flip.

“Rollback changes after B accepts writes. Read rollback while A is authoritative can be simple, but reverting write authority after cutover requires a verified reverse replay or other recovery path that preserves B-only writes. I would test fencing failure, consumer crashes, schema mismatch, deletes, backlog growth and source or destination outage. My alternative is to retain A as write authority for longer and use B only for reads, accepting operational cost to reduce transition risk. A maintenance pause could simplify the transfer only if the business changes the availability requirement.”

The senior answer should be probed on the actual fencing and durable acceptance implementation; those depend on system capabilities not supplied here. These designs have been reasoned through, not implemented or load-tested. A useful next drill for either candidate is to trace one acknowledged write through a crash at every stage and identify where its durable recovery record lives.
